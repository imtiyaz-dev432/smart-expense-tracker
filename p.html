1 Forgot Password

9 bugs across validation, security, and rollback.

#01 Redis key collision — otp:verification: reused for reset
Critical
Before
redis_client.setex( f"otp:verification:{user.email}", 300, hashed_otp) # Overwrites the signup verification OTP!
After
redis_client.setex( f"otp:reset:{user.email}", 300, hashed_otp) # Separate namespace — both coexist ✅
Attack scenario: Attacker knowing only a target's email can repeatedly trigger /forgot-password — each call overwrites the target's signup OTP, causing permanent email verification failure. A DoS via enumeration alone.
#02 success: False leaks user existence
Security
Before

After
GENERIC = "If the account exists, a password reset OTP has been sent." if not user: return jsonify({ "success": True, # uniform ✅ "message": GENERIC }), 200
#03 Message leak — different text for exists vs not-exists
Security
Before

#15 OTP not deleted — replay attack
Security
Before
try: user.password = generate_password_hash(new_password) db.session.commit() except: db.session.rollback() return 500 # ❌ OTP still in redis for 5 min # Attacker who saw the OTP can replay

3 Income Model

3 bugs — including a dangerous cascade direction that could delete users.

#20 Cascade on wrong side — deleting Income deletes User!
Dangerous
Before
# In Income model: user = db.relationship("User", back_populates="incomes", cascade="all, delete-orphan") # ❌ Deleting an income deletes the user!
After
# In Income model — no cascade: user = db.relationship("User", back_populates="incomes") # In User model — cascade belongs here: incomes = db.relationship("Income", back_populates="user", cascade="all, delete-orphan")
Data-loss bug: Cascade flows parent → child. Placed on the many-to-one side (Income → User), deleting a single income would cascade-delete the entire user — all their expenses, categories, other incomes, everything.
#21 DateTime timezone naive
High
Before
date = db.Column(db.DateTime, default=datetime.now(timezone.utc)) # Column is timezone-naive — tz info lost on save
After
date = db.Column(db.DateTime(timezone=True), default=lambda: datetime.now(timezone.utc))
#22 Float for money (deferred)
Deferred
Float loses precision for money (0.1 + 0.2 = 0.30000000000000004). Should be Numeric(12, 2) → Decimal. Deferred for MVP simplicity — note for future refactor.

§ Concepts Learned (Yesterday)

8 mental models from yesterday's session.

1 Redis key namespacing prevents cross-flow DoS

Different flows must use different prefixes: otp:verification: for signup, otp:reset: for password reset. Sharing a prefix means one flow silently invalidates the other — a DoS primitive.

2 Enumeration protection has three layers

Status code (always 200), message text (identical), and timing (advanced — pad with time.sleep). Most implementations miss the message-text layer while getting the status code right — success: false quietly leaks what the message tried to hide.

3 Replay attacks need explicit OTP deletion

After a successful password reset, the OTP must be deleted from Redis. Otherwise the same OTP remains valid for its full TTL — an attacker who intercepted it can replay the reset a second time within the window.

4 Cascade direction: parent → child only

cascade="all, delete-orphan" belongs on the parent side (User.expenses). Placed on the child side (Expense.user), deleting a single child deletes the entire parent — a silent mass-delete.

5 Redis returns bytes — always decode

redis_client.get() returns bytes by default. Comparing bytes to a str (verify_hashed_otp(stored, otp)) silently fails — the comparison is always False. Always check isinstance(stored, bytes) and .decode('utf-8').

6 (x or "").strip() — the None-safe string pattern

data.get('x').strip() crashes on missing/null. (data.get('x') or '').strip() collapses None to empty string before the string op runs — safe and concise.

7 Case preservation depends on field semantics

Labels (source, category) — case normalization optional. Free text (description) — case must be preserved. "Meeting with John" is not the same as "meeting with john".

8 Silent no-ops are the worst bugs

If a PATCH route validates input but never assigns to the model, the API returns "success": true while doing nothing. No error, no warning — the user thinks their change was saved. Always check that the assignment line exists after validation.
